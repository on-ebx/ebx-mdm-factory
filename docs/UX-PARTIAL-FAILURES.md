# UX lot D - partial failures as a real outcome (2026-10-14)

Branch `feature/ux-partial-failures`, from `main` 66bedf75 (every UX lot, wave C included). Source: the coordinator's live replay of 2026-10-13 (project UxCrmSf2) analysed with the
product owner. Status: coded, tests green (`tools/test_local.sh`), NOT deployed, NOT seen running. **This lot changes the data model (XSD): Tomcat must be restarted.**

## The problem

A partial failure was only recognised by parsing the English sentence of the job ("finished with failures on: SALESFORCE", "1 entity configured, 2 refused"). The stored job status
was DONE, so the Cockpit, the REST jobs route, other tabs and the next steps all saw a success; nothing said which tables or objects were missing; nothing warned before the next
step. The intake chain already had the right model (`IntakeChain.status = DONE_WITH_REJECTS`, `docs/AUTOMATIC-INTAKE.md`): this lot gives the job queue the same.

## 1. A real status

- `tools/build_xsd.py` (XSD regenerated by it, never by hand): `FactoryJob.status` gains `DONE_WITH_FAILURES` ("Done with failures" / "Terminee avec des echecs"), and the table gains
  one field, `detail` (text, 4000 characters; `FactoryPaths.FactoryJob.DETAIL`, also in `FactoryJobAccessRule.CREATE_LOCKED_FIELDS`). The table only had `message` (2000 characters, a sentence);
  the failed items need a structured place. XSD evolution is additive (an enumeration value and an optional field): no data is touched.
- Typed signal: `FactoryJobQueue.PartialOutcome` (checked exception, like `ExpectedFailure`) carries the job's sentence and the failed items. `runHandler` turns it into
  status `DONE_WITH_FAILURES`, message = the sentence, detail = `PartialFailures.toJson` (`{"total":4,"items":[{"id","label","reason"}]}`, never longer than the column: reasons are cut first,
  then the last items; `total` is always kept). Nothing is rolled back: the work that succeeded stays.
- Who throws it:
  - **Landing run** (`LandingRun.judgeOutcome`, both `HANDLER` and `RESUME_HANDLER`): judged per TABLE, no longer per application (lot C2's `allSourcesFailed` read "every
    application has a failed cell", so an application with 1 table of 2 failed counted as a total failure). Every table failed -> FAILED (red, as before); some failed, some loaded ->
    `DONE_WITH_FAILURES`; the items are the tables with a failed cell in the progress grid, labelled `SOURCE.Table`, with the reason of their first failed cell. A run still paused on
    a key, or stopped, is left as it is.
  - **Matching configuration** (`MatchingConfigureRun`): refused objects (`result.refused`, "Entity: reason") -> `DONE_WITH_FAILURES`. The parent `PipelineStep` is unchanged.
  - **Matching run** (`MatchingRunRun`): objects that failed (`failed`, "Entity - reason") or were refused while at least one ran -> `DONE_WITH_FAILURES`; every object failed and none ran stays
    FAILED (lot MT); refused-only is `DONE_WITH_FAILURES` too. The `PipelineStep` keeps ending FAILED when an object failed.
  - **Staging and master builds**: no per-entity partial case exists (they are stage-based: model then load, one job, and rows held back have their own review, `DONE_WITH_REJECTS`
    of the intake chain / the rejects review). Nothing changed there.
- One classification for every reader: `wizard/JobOutcome.display(kind, status, message)` returns `PARTIAL` (amber "Finished with failures") for the stored status. `RecentTasks` (the wizard
  and the Cockpit lists) uses it and shows the job's sentence. `JobOutcome.completed(status)` (DONE or DONE_WITH_FAILURES) replaces `DONE.equals` in `SourcesRun` / `DeducedScanRun` (their
  queries also list the new status; these kinds never produce it, it is defensive). `jobnotice.js` (end-of-task toast) reads the status only (`partial(job)`), `tools/jobnotice_test.js` updated.
  The REST jobs route (`FactoryJobStatus`) answers the stored status as is, and for a `DONE_WITH_FAILURES` job also `failedTotal` and `failedItems[]` (`id`, `label`, `reason`).
- **History**: the message-text parsing is gone from the toast and from every new job; it survives in ONE place, `JobOutcome.legacyReportsFailures`, only for DONE rows written before this lot
  (they cannot be corrected in the data): "finished with failures" and, for MATCHING_CONFIGURE / MATCHING_RUN, "N refused" with N > 0 still read amber in Recent tasks.

## 2. What is missing, and redoing only that

New pure classes in `wizard/`: `PartialFailures` (items, the stored detail, "what is STILL missing", sentences, the Summary's open points) and `PartialFailuresView` (the HTML blocks).
`FactoryJobStatus.lastOutcomes(factory, projectId)` reads, in one scan, the latest job that ended with an outcome (DONE, DONE_WITH_FAILURES, FAILED; a cancelled or interrupted one resolved
nothing) of each group: landing (`LANDING_RUN` + `LANDING_RUN_RESUME`), configure, run. `WizardPage.Model.lastOutcomes` carries it; it is not the 10 rows of Recent tasks (a failure stays
unresolved however many tasks came after it).

- **Step 3** (under the grid of a finished run): "2 of 4 tables were not loaded: SALESFORCE.Account, SALESFORCE.Contact", one line per table with the reason of its cell, and the button
  "Retry the 2 failed tables" (`LANDING_RETRY_FAILED`, DESIGN right, same `generateLanding` gate as a run). The list is recomputed on the server at the click from the job queue and the tables'
  own status (a table loaded or unticked since is left out; "Nothing to retry" when none is left). `LandingRun.start(..., onlyTableIds)` has a new table filter (`params.onlyTableIds`): the grid,
  the KEY and FLOW stages and the verdict concern only these tables. **The TABLE stage (the landing model of the application) and the LOAD stage are per application by construction**
  (`LandingGenerator`, `LandingFlows#load`): the other tables of the same application are generated and read again with them - one incremental read for a table with a change column,
  harmless for the others. The plain "Run again" button stays.
- **Step 6**, above Run: "2 objects were refused when configuring: Organisation (reason), OrganisationAddress (reason)" with "Configure these 2 objects again" (the existing
  `MATCHING_CONFIGURE`: it skips the objects already up to date, so it only redoes the refused ones). Only objects whose plan is still ACCEPTED (not applied) are listed. Below the live
  table, "N objects failed in the last run: ..." with their reasons (the Run button above runs them all again; there is no per-object run).

## 3. Warn before the next step, never block it

- Until now the Staging step was BLOCKED while any ticked landing table was not loaded (`wizard.blocked.needLandingLoaded`), so "Continue to the staging" never showed after a partial landing.
  `WizardSnapshot.landingGapIsKnown` (set by `ProjectWizardUserService.model()` from `PartialFailures.landingGapIsKnown`) opens the step when the latest landing job ended with failures, at
  least one ticked table is loaded and EVERY ticked table that is not loaded is one the run reported as failed. Any other gap (a table never run, one waiting for its key) keeps the step
  closed as before. `WizardRules.suggestedStep` no longer pulls the person back to the landing once they went on and the staging exists. **Other users of the strict rule are unchanged**
  (`DistributionRunner`, `IntakeReadinessReader` keep `allTickedTablesLoaded`).
- Step 3, under "Continue to the staging": "The staging will be built without SALESFORCE.Account and SALESFORCE.Contact. Load them later and build the staging again to add them."
  (more than 4 names: "A, B, C, D and 3 more"). **Caution**: the staging pipeline does not filter on the landing table status, so a ticked table that failed may still be proposed as a staging
  entity (empty); the sentence promises less than "excluded" for that reason ("load them later and build again"). To be checked live (below).
- Step 6, under the Run text: "Run matching will leave out Organisation and OrganisationAddress: refused when configuring. Configure them again first." Run itself is not disabled by it.
- "Continue to the master": not relevant - the staging and master builds have no partial case (nothing to warn about).
- **Summary** (`PartialFailures.openPoints`, called by `buildSummary`): an unresolved partial failure is a red (ERROR) open point with a link to its step - "2 landing tables are not loaded:
  A, B" -> Landing, "2 objects were refused when configuring: ..." -> Matching, "N objects failed in the last matching run: ..." -> Matching (an object already flagged "the last matching
  run failed" is not repeated). It goes away when a later run of the same kind succeeds (it becomes the latest job) or when the items are fixed another way (table loaded, plan applied).

## Not done / limits

- `LandingRun#judgeOutcome`, the `MatchingConfigureRun` / `MatchingRunRun` throws, `FactoryJobStatus.lastOutcomes` and the `LANDING_RETRY_FAILED` action need an EBX repository: not unit tested;
  the pure rules they rest on are.
- A retry whose LOAD reads the whole application again for tables without a change column (see above).
- No per-object matching run; no "Continue to the master" warning (no partial case there).
- The REST jobs route lists `failedItems` only in the 10 `recent` jobs it already returns.
- A failed run that loaded NOTHING stays FAILED (red) with no item list: the plain "Run again" is the way, as before.
