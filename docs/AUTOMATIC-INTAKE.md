# Automatic intake (landing -> staging -> master -> matching without anyone launching the chain)

Backend lot, 2026-10-05, branch `feature/automatic-intake-engine`. **Status: coded, unit tests green (`tools/test_local.sh`, all green), NOT deployed, NOT seen running.** Nothing in this
lot has run in EBX. The screens (set-up, running, summary delta: `docs/mockups/automatic-intake/*.dc.html`) are a separate lot built on the contract of section 6 - see section 11.

## 1. Principle (decided, not redesigned here)

- **The queue IS the landing itself**: a landing row with `_status = 'NEW'` (or empty) waits. The existing incremental transfer (`StagingLoader` scope `new`,
  `transfer.IncrementalTransfer.NEW_SCOPE_PREDICATE`) consumes it. A **scripted trigger on the landing tables is only a wake-up**.
- A chain starts after a **quiet period** (default 60 s with no new row), never later than the **longest wait** (default 10 min) after the first waiting row, only for
  at least the **minimum number of rows** (default 1). An application able to say "my batch is complete" can call REST; when the Factory itself ends a landing read of a source,
  the chain starts right after it.
- A chain = one instance of the workflow `MdmFactoryPipeline` in incremental mode (`loadLanding=false`, `stagingScope=new`, `scope=incremental`, `reviewRejects=false`),
  **one at a time per project**. Rows arriving during a chain wait for the next one.
- Rows held back (staging rejects): a **non-blocking** review task for the data steward (workflow `MdmFactoryRejectReview`); an optional **stop threshold** (% of the rows read held
  back) stops the chain at staging and pauses the intake as soon as AT LEAST that share is held back (threshold 5 stops at 5 of 100; threshold 100 = stop only when every row read is held back).
- Switched on only after the first full load (readiness gate).

## 2. Data model

`tools/build_xsd.py` (generated `MdmFactory.xsd` committed with it):

| Table | Fields added |
|---|---|
| `Project` | `intakeState` (`OFF` default / `ON` / `PAUSED`; empty = OFF), `intakePauseReason`, `intakeEnabledBy` (user id), `intakeEnabledAt`, `intakeReviewRejects` (boolean, empty = true), `intakeStopRejectPercent` (int, empty = never stop) |
| `ProjectSource` | `intakeQuietSeconds` (60), `intakeMaxWaitMinutes` (10), `intakeMinRows` (1), `intakeBatchSignal` (boolean, informative). Empty = default, so rows written before the lot behave as the defaults |
| `IntakeChain` (new) | `id` = random UUID string generated by the engine (also the token of the workflow data context), `project`, `startedAt`, `endedAt`, `reason` (`QUIET`/`MAX_WAIT`/`BATCH_COMPLETE`/`MANUAL`/`SWEEP`), `sources` (comma-separated), `rowsWaiting`, `written`, `unchanged`, `rejected` (decimals), `status` (`RUNNING`/`DONE`/`DONE_WITH_REJECTS`/`STOPPED`/`FAILED`), `message`, `workflowKey` |

A second packaged model, `WEB-INF/ebx/schemas/IntakeSignal.xsd` (hand-written like `DistributionOutbox.xsd`, `xmllint --noout` clean): table `Signal`, primary key `sourceSystem`,
fields `lastRowAt` (dateTime), `updatedBy`. One dataset `MdmFactoryIntakeSignal` per project **in the project's landing dataspace** (`ebx.IntakeSignalInstaller`, the
`doCreateRoot` pattern of `DistributionOutboxInstaller`): a table trigger cannot open `execute transaction`, it can only write through its ambient transaction, which is scoped to its
own dataspace (measured in the distribution lot). The installer pre-creates one row per source, so the trigger's create branch is only a fallback (no race between two first writers).

`IntakeChain` is also listed in project deletion (`ProjectDeleter`, batched like `DistributionEvent`) and in the retention purge (`FactoryRetention`, same `historyRetentionDays`;
a RUNNING chain is never purged). A step reset from LANDING / STAGING / MASTER and a project deletion force `intakeState = OFF` first (`Intake.forceOff`): the landing triggers
and the signal dataset disappear with the landing objects. (A reset from MATCHING does not touch the landing and leaves the intake alone.)

## 3. The landing triggers (`intake.IntakeTriggerBody`, `ebx.IntakeTriggerInstaller`)

Per ticked landing table of every source (model `LandingNames.modelName(project, source)`), three triggers, declared with the data-model `set_script_trigger` (scope `table`), authored
with the scripting `get_script`/`update_script`, published with `publish_data_model` - **the mechanism `DistributionTriggerInstaller` proved live** (declare everything; publish once
if something was newly declared, because a never-published script has no revision history; author; final publish; script path `data-model/<Model>/root/<Table>/@trigger/<Name>`,
fallback by `scriptTypeId`). The generic steps are in `ebx.ScriptTriggerOps`; `DistributionTriggerInstaller` was deliberately left untouched (no live run is possible here to prove a
refactor of it behaviour-neutral). Uninstall = `unset_element_property(property="triggers", item=<Name>)` per trigger, then one publish per model - never without `item`.

The columns the before-modify trigger watches are the table's real fields (`describe_table`) minus the factory's technical fields (`_sourceId`, `_sourceSystem`, `_loadId`,
`_receivedAt`, `_rowHash`, `_status`); fallback when `describe_table` answers nothing: the table's `LandingColumn.fieldName` rows. Every column is written as a **quoted identifier**
(`"FROM"` compiles). A landing model rebuilt later loses its triggers: switch the intake off and on again (the 5-minute sweep covers the gap meanwhile).

### 3.1 `IntakeAfterCreate` / `IntakeAfterModify` (wake-up; the two differ only by the entry point `onAfterCreate` / `onAfterModify`)

```
// Generated by ebx-mdm-factory (automatic intake, docs/AUTOMATIC-INTAKE.md). Do not edit: the intake installer rewrites it.
// Wake-up only: touches the signal row of this source; the queue is the landing table itself (rows at _status NEW or empty).
uses core.data as db;
uses core.datetime as dt;
uses core.complex as cp;
references model "IntakeSignal" from module "ebx-mdm-factory" as signal;

function isWaiting(status: string): boolean
begin
	return isNull(status) or status = 'NEW';
end

export procedure onAfterCreate()
begin
	if not isWaiting(_ebx.record."_status") then return;
	const signalDataset := db.findDataset(_ebx.dataspace, 'MdmFactoryIntakeSignal');
	if isNull(signalDataset) then return;
	const signalTable := db.findTable<signal.Signal>(signalDataset);
	var signalPk := cp.primaryKeyOf<signal.Signal>();
	signalPk.sourceSystem := 'Salesforce';
	const moment := dt.now();
	const existing := db.lookupRecord(signalTable, signalPk);
	if isNull(existing) then
	begin
		var created := db.recordOf(_ebx.transaction, signalTable);
		created.sourceSystem := 'Salesforce';
		created.lastRowAt := moment;
		db.saveRecord(created);
		return;
	end
	if not isNull(existing.lastRowAt) then
	begin
		if dt.addSeconds(existing.lastRowAt, 5) > moment then return;
	end
	var touched := db.lookupRecordForUpdate(_ebx.transaction, signalTable, signalPk);
	if isNull(touched) then return;
	touched.lastRowAt := moment;
	db.saveRecord(touched);
end
```

### 3.2 `IntakeBeforeModify` (example with three source columns)

```
// Generated by ebx-mdm-factory (automatic intake, docs/AUTOMATIC-INTAKE.md). Do not edit: the intake installer rewrites it.
// Keeps the queue truthful for rows an application writes straight into this table: a change of a SOURCE column puts the row back at _status NEW,
// unless the writer sets _status itself (the factory's own writes move _status NEW -> STAGED/REJECTED, so they are left alone).

function differs(a: string, b: string): boolean
begin
	if isNull(a) and isNull(b) then return false;
	if isNull(a) or isNull(b) then return true;
	return a <> b;
end

export procedure onBeforeModify()
begin
	if differs(_ebx.record."_status", _ebx.nextRecord."_status") then return;
	if isNull(_ebx.nextRecord."_status") or _ebx.nextRecord."_status" = 'NEW' then return;
	if differs(_ebx.record."FIRST_NAME", _ebx.nextRecord."FIRST_NAME") then
	begin
		_ebx.nextRecord."_status" := 'NEW';
		return;
	end
	if differs(_ebx.record."LAST_NAME", _ebx.nextRecord."LAST_NAME") then
	begin
		_ebx.nextRecord."_status" := 'NEW';
		return;
	end
	if differs(_ebx.record."EMAIL", _ebx.nextRecord."EMAIL") then
	begin
		_ebx.nextRecord."_status" := 'NEW';
		return;
	end
end
```

A table with zero source columns gets a no-op body. Generated source literals are escaped backslash-style (`\'`, `\\`), never doubled quotes.

### 3.3 Why none of the Factory's own writers can fight the before-modify rule

The rule only acts when the writer does NOT change `_status` itself, the resulting status is not already NEW/empty, and a SOURCE column really changed. Every writer of landing rows:

| Writer | What it writes | Why safe |
|---|---|---|
| Connectors landing flow (the Factory's read) | source columns + `_loadId`, `_receivedAt`, `_rowHash` + `_status` with rule `ALWAYS` = `NEW` (`landing.LandingFlow`, incremental lot) | `_status` either changes (STAGED/REJECTED -> NEW) or is already NEW: the trigger returns. With an old flow whose `_status` rule was `IF_EMPTY` a changed row would stay STAGED: the trigger sets NEW, which is the correct outcome |
| `StagingLoader` landing status flush (`flushLandingStatus`) | `_status` only (NEW -> STAGED/REJECTED; in scope `all` possibly STAGED -> STAGED) | status changes, or no source column changes: the trigger never requeues |
| `LandingKeyChange` | deletes the rows of a table (`doDelete`), then a reload creates them | no modify; the reload's creates are the legitimate wake-up |
| An application pushing rows | source columns only, no technical field | exactly the case the trigger exists for: a changed source column puts the row back at NEW (a new row is created with `_status` empty, which also counts as waiting) |

Grep of the module's writers of landing datasets (2026-10-05): `StagingLoader`, `LandingKeyChange`, `ProjectDeleter`/`StepResetter` (whole dataspace deletions) - nothing else
writes a landing row.

## 4. The decision (`intake.IntakeDecision`, pure, unit-tested)

Per source with something waiting (`IntakePending.isPending`) - or every source when the person pressed "Process now":

- manual: due at once, `MANUAL`; the application said "complete" (REST or the Factory's own read ended): due at once, `BATCH_COMPLETE`;
- else due at the earlier of *last row + quiet period* (`QUIET`; `SWEEP` when the knowledge came from the safety sweep) and *waiting since + longest wait* (`MAX_WAIT`).
- Only a source that is due gets its NEW rows counted (`createRequestResult(NEW_SCOPE_PREDICATE).getSize()` per ticked landing table). 0 rows: nothing to do, pending cleared.
  Fewer than the minimum: keeps waiting until the longest wait (`QUIET`/`SWEEP` only; `MAX_WAIT`, `MANUAL`, `BATCH_COMPLETE` launch with one row).
- Never launches when the state is not `ON` or a chain is running. `RejectThreshold`: `rejected * 100 >= percent * read` ("at least"), integer maths, read 0 never stops, 0 rows held back never stops (a threshold of 1 with 0 rejected is not a stop), exactly at the threshold
  DOES stop. Threshold 100 = stop only when every row read is held back. `IntakeReadiness`: three blocking lines (published pipeline declares `intakeChain`; every ticked landing table LOADED; staging and master loaded once - the proofs of
  `DistributionRunner`/`MasterStagingReadiness`/`DistributionMasterReadiness`) and one informative ("N rows held back still to review").

## 5. The engine (`ebx.IntakeEngine`) and the workflow side

One daemon thread `ebx-mdm-factory-intake`, `ScheduledExecutorService`, a tick every 10 s, own system session (`createSystemUserSession("mdm-factory-intake")`), started in
`FactoryModuleRegistration.handleRepositoryStartup` (a failure to start never takes startup down), stopped in `handleRepositoryShutdown`; every pass is caught, one project's failure
never stops the others. Per tick: (1) close the RUNNING chains whose instance ended; (2) for each project with `intakeState = ON`: read the signal of each source (primary-key lookup),
update the in-memory `IntakePending`; (3) at startup and after every chain: **one re-count** of the NEW rows per source (rows that arrived during a chain or inside the trigger's 5 s throttle
window are never stranded); (4) every 5 minutes a **safety sweep** counts the sources the signal showed nothing for (covers lost triggers; measured cost of such a count on a 230,722-row
landing table: under 5 s, so not more often); (5) `IntakeDecision`; (6) launch.

**Launch**: the `IntakeChain` row is created FIRST (status RUNNING, id = UUID), then `PipelineWorkflowLauncher.launchIntake` (on its own thread, see below) starts `MdmFactoryPipeline` (inputs set only when the published
model declares them) from the engine's system session - the pattern `ebx-data-catalog`'s `TagReviews` proved from a system context; the instance key is stored on the row. The running chain IS
the project's RUNNING row, so a restart loses nothing. A published model that does not declare `intakeChain` is never launched on: the status says "the published MdmFactoryPipeline
predates automatic intake: import and publish tools/workflow/MdmFactoryPipeline.json" and the switch-on is refused. A launch that fails marks the chain FAILED and pauses the intake.
**Which thread launches**: neither `ProcessLauncher.launchProcess` in the local Javadoc nor `javap` says whether the first script task of the new instance (here the staging load) runs in the launching thread
before the call returns (the doc only says a script task bean "must not create any threads"; the "synchronous" launching mode concerns the first USER task). So the engine does not depend on it: the launch is made on a
separate thread (`ebx-mdm-factory-intake-launch`), never under the project lock and never on the tick thread; the tick waits at most 30 s for it and goes on (a warning is logged). The chain row already exists
(RUNNING), so the project counts as having a chain running; a RUNNING row whose launch has not returned is in an in-memory `LAUNCHING` set and is not closed as an orphan. The chain never needs the tick thread: its gate reads
the `IntakeChain` row and the project, nothing of the engine's memory.

**Follow-up** (`WorkflowEngine`, all javap-checked): `isProcessInstanceRunning` (running / not), `getProcessInstance(...).isInError()` (an instance in error ends the chain FAILED: replay or
terminate it, then Resume), and for an ended instance `getProcessInstanceHistory(...)`: the data-context variables `stagingWritten`/`stagingRejected`/`stagingStopped`/`stagingResult`
(`ProcessInstanceStep.getDataContextAfter`) and `getTerminationType()` (`TERMINATED_FORCED` = failed). **A completed instance is not assumed to stay readable**: the fallback is the
`PipelineStep` rows whose `via` contains `intake <chain id>` (a FAILED step fails the chain; the staging step's detail gives the counts); a chain with no evidence at all is FAILED. A RUNNING row
with no workflow key (the JVM died between the two writes) is closed after 2 minutes. When the chain ends: `written`/`unchanged`/`rejected`, status `DONE` / `DONE_WITH_REJECTS` / `STOPPED` /
`FAILED`; on `STOPPED` and `FAILED` the project goes `PAUSED` with a reason (`stopped: 6 % of the rows held back`, `failed: ...`); a re-count follows; a queued "Process now" starts next.

**Non-blocking review**: when a chain ends with rejects and `intakeReviewRejects` is true, `MdmFactoryRejectReview` is launched for the project unless one is still running (in-memory key, and after
a restart `getProcessInstanceKeysForDataContextVariable(..., "projectCode", code)` which answers ACTIVE instances). A missing publication is a warning on the status
(`rejectReview.warning`); the chain stays `DONE_WITH_REJECTS`.

**Gate (`workflow.PipelineLauncher` + `workflow.IntakeGate`)**: today the instance CREATOR must hold the role `pipelineLauncherRole` (administrators when empty). An intake chain's creator is the
engine's system session, so ONE narrow path was added: if the data context declares `intakeChain` (`DataContextReadOnly.isVariableDefined` - an old publication does not, and reading it would throw),
and an `IntakeChain` row with that primary key exists, is `RUNNING`, belongs to the project named by the bean's `projectCode`, that project's `intakeState` is `ON` **or `PAUSED`** and the user in
`intakeEnabledBy` holds the role NOW, the work runs as `Actor.as(intakeEnabledBy, "intake <chain id> · workflow <instance key>")`. Anything else falls through to the creator check, unchanged.
Who could forge it: launching `MdmFactoryPipeline` needs its `permissionsOnInstances.create` (administrators); an administrator with a made-up token falls through to the creator check; with
a REAL token (an unguessable UUID that exists only in `IntakeChain`) the only effect is that the project's own incremental pipeline runs as its enabler, while a chain is RUNNING. Residual
risk, named: if `create` is ever widened to people who can also READ `IntakeChain`, such a person could run that project's incremental pipeline - keep the table's read access to administrators.
Revoking the role of whoever switched the intake on stops the automation at its next step.
**ON or PAUSED**: `Intake.pause` is allowed while a chain runs; a pause means "no NEW chain, the running one finishes". The staging step may already have passed, so denying PAUSED would send the master
and matching steps to the creator check (a system user) and end the instance in error halfway. The `RUNNING` chain row proves the chain was launched while the intake was ON; only OFF denies. A user
switch-off is refused while a chain runs (below), so OFF with a RUNNING chain only comes from the forced OFF of a deletion or a step reset (the objects are going away).

`workflow.StagingLoadTaskBean`: new optional input `maxRejectPercent`, new output `stopped` (`"true"`/`"false"`, `RejectThreshold` on the loader result's own `read`/`rejected`; no threshold: always
`"false"`). `module.xml` declares both (en/fr). `tools/workflow/MdmFactoryPipeline.json`: variables `intakeChain` (in), `maxRejectPercent` (in), `stagingStopped` (out, no default); node 3's
`stopped` mapped to `stagingStopped`; new condition node 11 "Too many rows held back?" (`ConditionIsValueEqualsTo`, `${stagingStopped}` = `true`) between node 3 and node 4: true -> new end node 12
"Stopped: too many rows held back" (`ScriptTaskUpdateWorkflowLabel`), false -> node 4. Existing node ids unchanged; a launch passing neither new input behaves as before.
`tools/workflow/MdmFactoryRejectReview.json`: one user task (the review of `TransferReject` of the project at stage STAGING), offered to `Badministrator`, accept label "Reviewed", no reject.

Failure modes (`OperationException`, English sentence): not an operator ("Only an administrator, or a holder of the pipeline launcher role..."); project/application not found; settings out of range
(quiet 5-3600 s, longest wait 1-1440 min and not below the quiet period, min rows >= 1, percent 1-100 or empty - `IntakeSettings.validate`); switch-on refused with the first blocking readiness line;

`switchOff` while the project has a RUNNING chain ("A chain is running: pause the intake, wait for it to end, then switch it off." - `intake.IntakeSwitchRules`; it can never lock anyone out: a pause is always allowed and an instance stuck in error is closed FAILED by the engine; the forced OFF of a deletion / step reset stays unconditional); `processNow` when not ON; `batchComplete`: "Forbidden: ..." without write access.
```java
public static ObjectNode readNow(Session s, Adaptation factory, String projectCode, String sourceSystem) throws OperationException   // operator; CONNECTORS application; intake not OFF
```
**"Read now"** (2026-10-06) queues a plain landing load of ONE application as a background job and returns at once with the job (`{"project","sourceSystem","started","jobId","merged","position"}`). Mechanism: `LandingSourceRun.startRead`
-> `FactoryJobQueue.enqueue` with kind `LANDING_READ_RUN` (registered in `FactoryJobKinds`, resource LANDING, like `GENERATE`/`PLAN` and the one-click `LandingRun`: never concurrent with them for the project) whose handler,
`LandingSourceRun.READ_HANDLER`, calls `LandingFlows.load(session, factory, projectSourceId, ProgressNote.NONE, handle)` - the same call the landing step makes, without the model/flow rebuild `GENERATE` does first; the job's own Handle reaches the load's Stop button;
a table that fails to load ends the job with an expected failure carrying the first reason. A load that ends without a failure calls `IntakeEngine.sourceLoaded` by itself, so the chain starts right after the read. Refusals: not an operator;
intake OFF ("switch it on first"; ON or PAUSED are accepted: a paused intake reads and the rows wait for the resume); the application is not CONNECTORS ("the application pushes its own rows, there is nothing to read"); unknown project/application.
The "next read by the Connectors flow: tomorrow 01:00" line of the mock-up is NOT provided by this lot (the flow's schedule is not read here).

**A total reject is not an error in an intake chain** (2026-10-06). `StagingLoadTaskBean` has a new optional input `intakeChain` (bound to `${intakeChain}` on node 3; non-empty = an intake chain; trusted for nothing but this routing choice, the gate having proved the token before the work ran).
For an intake chain a load that rejected every row read does NOT throw: it sets `stopped = "true"` (node 11 routes to the stop end node 12, "Stopped at staging: rows held back, master load not run") and the outputs carry the counts. A person-launched pipeline keeps the audit's throw.
The engine decides STOPPED from the counts and the project's own threshold (`IntakeChainOutcome.statusOf`), never from `stagingStopped` alone: no threshold + partial rejects -> `DONE_WITH_REJECTS`; no threshold + total reject -> `DONE_WITH_REJECTS` (review opened per `reviewRejects`, intake NOT paused);
threshold reached (`RejectThreshold.reached`, "at least": `rejected * 100 >= percent * read`; exactly 5 of 100 at threshold 5 stops, 4 of 100 does not; a total reject reaches every threshold, so threshold 100 = stop only when every row read is held back) -> `STOPPED` and paused; threshold not reached -> `DONE_WITH_REJECTS`; nothing held back -> `DONE`. A `FAILED` `STAGING_LOAD` step that is only a total reject (history counts, or the step's own sentence
"Every source row read was rejected") is not a failure of the chain in the `PipelineStep` fallback either.

```json
      "dueAt": "2026-10-05T14:41:12Z",                        // starts then if nothing new arrives ("starts after 60 s of quiet")
      "latestAt": "2026-10-05T14:50:00Z",                     // "at the latest 14:50" = pendingSince + longest wait
      "state": "RECEIVING",                                   // IDLE | RECEIVING | DUE | RUNNING (RUNNING = in the current chain)
      "reason": "QUIET",                                      // why it would start: QUIET | MAX_WAIT | BATCH_COMPLETE | MANUAL | SWEEP
      "batchCompletePath": "/ebx-mdm-factory/rest/v1/projects/Personnes/intake/Salesforce:complete" } ],
  "currentChain": null,                                       // the RUNNING chain (same shape as a chains[] entry) or null
  "queuedAfterChain": false,                                  // "Process now" pressed during a chain
  "chains": [ {                                               // last 10, newest first (the running one included)
      "id": "uuid", "startedAt": "...Z", "endedAt": "...Z" /* null while running */, "reason": "QUIET",
      "sources": ["Salesforce"], "rowsWaiting": 312, "written": 300, "unchanged": 12, "rejected": 0,
      "status": "DONE",                                       // RUNNING | DONE | DONE_WITH_REJECTS | STOPPED | FAILED
      "message": null, "workflowKey": "..." } ],
  "rejectReview": { "open": false, "heldBack": 3, "warning": null },   // heldBack = cached count of unresolved staging rejects (null before the first count)
  "engineRunning": true,                                      // false: the engine thread did not start, nothing starts by itself
  "mayOperate": true,                                         // the CALLING session may change the intake (admin or pipelineLauncherRole): hide Pause / Settings / Process now / Switch on-off when false
  "serverTime": "2026-10-05T14:40:30Z"                        // compute "12 s ago" against this, not the browser clock
}
```
Mock-up columns: Started = `startedAt`, Application = `sources`, Rows = `rowsWaiting` / `written` + `unchanged` (the Factory does not tell "new" from "changed": `written` is the rows written to staging,
`unchanged` those found identical), Held back = `rejected`, Took = `endedAt - startedAt`, Result = `status` (+ `message` for the stop line). The readiness lines are only evaluated while the intake is not ON.

## 10. Open risks (ranked)

1. A trigger that throws breaks the landing write of the application: the bodies are minimal and null-guarded, but the entry points were never compiled (point 1 above). Uninstall (`/off`) is the way out.
2. Cost of the per-row wake-up on a mass load (point 2), and lock contention on the single signal row of a source (the throttle limits it to one write per 5 s per source).
3. The engine's follow-up of a finished instance depends on what the workflow engine keeps (point 5); the fallback may give no counts (the chain is then `DONE` with zeros or `FAILED` "no result recorded").
4. `/on` is synchronous; the tick holds a per-project lock while counting or launching, so a batch-complete call or "Process now" can wait for it (status never does: it reads a published snapshot).
5. The status `label` is the source code and the next-read time of a Connectors application is not provided.

### 11.3 Live refresh of the running screen

`IntakeScreens.renderLive` writes the complete screen from `Intake.status` (no JavaScript needed). `wizard.js` ("automatic intake live panel"): every **5 s** (`data-mdmf-in-interval`) `GET /ebx-mdm-factory/rest/v1/projects/{code}/intake` with the session cookie
(same as the jobs banner), then repaints the cards' bodies (`cardBody`) and the chains' rows (`chainRow`) in place - these two mirror `IntakeScreens.cardBodyHtml`/`chainRowHtml`, labels come from `data-mdmf-in-labels`. Between two reads a one-second tick moves "Last row N s ago" and the quiet-period bar.
Every "ago" is computed against `serverTime` (offset = `serverTime` - browser clock at the last read, initialised from `data-mdmf-in-server-now`); clocks ("at the latest 14:50", the Started column) are shown in the **server's** zone (`data-mdmf-in-tz`) so the first paint and the repaint agree.
The step is reloaded **once** (the wizard's own `STEP_VIEW` round trip) when `state` changes, `engineRunning` changes, the list of applications changes, or a chain this page had seen running has ended - unless the person is typing in the settings panel (then it waits for the next read). A failed read shows the discreet
"not refreshed" hint and tries again at the next interval, never an alert. Polling stops when the element is gone (`document.body.contains`), and a screen whose step is not showing is not read.

### 11.4 What differs from the mock-ups, and why

- **No "every day at 01:00" / "next read by the Connectors flow" line** on a Connectors application (set-up and running): the backend does not read the flow's schedule (section 6.2). The set-up sentence says instead that processing starts right after a read run by the Factory itself and that a read launched elsewhere is picked up after the quiet period.
- **"Can be switched off at any time from the Cockpit"** became "Can be paused or switched off at any time from this screen": the Cockpit has no such control in this lot.
- **"Read now" is on the CONNECTORS cards** (2026-10-06, `INTAKE_READ_NOW`): a "Read now" button under the "Fed by EBX" hint of a Connectors application (hidden for a reader and never on a pushed application); it queues `Intake.readNow` (a plain landing load as a background job, section 6.2) and shows a notice; the chain follows the read by itself.
- **Quiet period / longest wait / minimum rows are real controls on the running screen too** (the Settings panel), saved by `Intake.saveSettings` without leaving the screen; the mock-up only had a Settings button.
- **Rows column**: "N new" is the count at launch (`rowsWaiting`); "written" and "unchanged" are added when the chain reports them (the Factory does not tell new from changed rows). Held back = `rejected`, "-" when unknown.
- **The Matching box** reads `Project.matchingTrigger` ("on each save" / "when launched"); the **Distribution box** is built from the targets the Summary already holds ("Kafka - on a schedule"), or "nothing set up".
- The readiness lines are worded from their `key` (so they follow the page language); the status's English `text` is only the fallback for an unknown key or a count it cannot word ("The project has no source yet").
- The stop threshold is "a checkbox and a number 1-100", empty when unticked; the pause reason of a stopped chain is the backend's own sentence (English), shown as data.

### 11.5 Gaps found in the backend contract (nothing invented, nothing changed)

1. ~~No per-application "read now" in the facade~~: `Intake.readNow` (section 6.2), button on the CONNECTORS cards.
2. `IntakeStatus.Source.label` is the application code today, so the cards show the code; the code is also what the batch-complete path carries.
3. No next-read time for a Connectors application (documented gap, section 6.2).
4. `pauseReason` and `chains[].message` are English sentences from the engine, not keys: shown as they are in both languages.
5. `rowsWaiting` is a cached count (never counted on the status path): null = "rows arriving", a stale number is possible between counts.
