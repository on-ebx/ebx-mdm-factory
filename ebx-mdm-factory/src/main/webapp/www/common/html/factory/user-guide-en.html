MDM Factory - user guide

The MDM Factory builds a master data hub in ON EBX from the applications that hold your records: it brings their data in, proposes one trusted record per person, company or product, and keeps the trail of where every value came from. This guide follows the wizard step by step.

How the wizard works

The wizard has eight steps, shown in the rail at the top. A step opens once the steps it depends on are done; a greyed step says, when you point at it, what it is waiting for. Nothing is generated from a proposal that nobody accepted: the factory proposes, you decide.

Long actions (reading an application, building a zone, loading data, asking the language model, running the matching) run in the background. You can leave the page: the work goes on, and the task banner and the Recent tasks list tell you how it ended.

The Help link next to the step name opens this guide at the section of the step you are on.

1. Project

Give the project a code and a name, say who owns it and where its master data will live. The code names the dataspaces the factory creates (code_Landing, _Staging, _Master), so choose it once.

The implementation style cards compare the usual ways of running an MDM. Consolidation - one golden record built from every application, which keep their own copy - is the one the factory builds today; the other cards are there to compare and are not selectable yet.

What may reach the language model: the factory can ask a language model for proposals. Choose whether it may see only the structure (names and types), or also a small sample of values. Your administrator sets the most the instance allows.

2. Sources

Add each application that holds the records you want to master (an ERP, a CRM...). Pick its connection, and the factory reads what it contains - tables, columns, a profile of the values - through the data catalog. If an application has no catalog entry yet, the onboarding panel walks you through creating one and scanning it; you never need to open Connectors or the catalog yourself.

An application without a readable structure (a file, an API with no schema) can be described by a sample file; the factory deduces its tables and asks you to confirm each one.

The trust rank of an application tells the matching which source wins when two disagree.

3. Landing

The landing zone is a faithful copy of each application's data inside EBX. One click plans it, finds each table's key, builds the landing tables, writes the flows and loads the data.

A table stops for you when no key is certain enough, and whenever the key comes from the language model: a key the model proposes is never applied on its own, whatever its confidence. Choose the key then opens on its proposal, already ticked: one click confirms it. Otherwise the wizard shows a sample and the candidate keys, and Study the key can ask the language model for an opinion. Once a table is built, its key is changed with Change the key..., which empties the table and rebuilds its flow.

4. Staging

The staging zone is your target model: one entity per business object (Person, Company, Address...) with the attributes you decide to keep, and a mapping from each application's columns to those attributes.

Propose the staging reads the landing and proposes entities, attributes and mappings; when a language model is configured it then unifies the applications into shared entities. Accept or reject each proposal - one by one, by entity, or above a confidence threshold. The Mapping matrix and the Feed designer show the same mappings as a grid and as a drawing; both are reachable from this step.

Quality rules and script constraints (a phone number check, a VAT number check...) are proposed here too. A rule in severity Reject stops a row before the master; a warning only flags it.

When every accepted attribute has a mapping, generate and load the staging. Rows that fail a blocking rule are held back and listed for review.

5. Master

The master zone holds one table per business object you accepted. The factory generates it, then fills it from the staging of every application, and records for each master record which source rows built it (the cross-references that record lineage shows).

6. Matching

For each business object the factory proposes a matching plan: which fields to compare, how close is close enough, and which pairs are sure matches versus pairs a person must look at. Simulate tries a plan on real records without changing anything. Configure writes it into Match and Merge; Run (every record) runs it over the whole table, Run (last loaded batch) only over the records loaded last.

The list of pairs to decide is shown ten groups at a time: the buttons at its foot page through it (for example "21-25 / 25"), and a line says how many more groups exist beyond the ones stored for the screen ("138 more groups not shown here"). The Merged and Different tabs show the true total when it is known, and "60+" or "100+" when the list is cut and the total is not; the list then says "60 of 1200 shown". Decide the first groups to reach the next ones. Merging every pair above a score, and simulating a plan, run as background tasks.

The results show the groups that were merged and the suspect pairs: a data steward decides each one (merge, or not the same), or merges every pair above a score.

7. Distribution

Choose the systems that receive the golden records (a Kafka topic, a REST API, a warehouse...) and when they receive them: on every change, on a schedule, or on demand. Nothing leaves EBX until a target is switched on. You can also publish the master as a data product in the data catalog.

The list of connections is read in the background and kept per person: the page says "Reading the connections..." until it arrives, "Connections not read yet" with a Refresh the connections button when nothing was ever read, and shows the last list while a newer one is read. The warehouse is only probed when you press Test the connection; creating the data product never probes it.

8. Summary and production

The summary says whether the project is ready, what is still open (rejected rows, suspect pairs, targets not switched on) and how long the last full run took. From there:

  • Launch now runs the whole chain - landing, staging, master, matching - as an EBX workflow that stops on rejected rows to review.
  • Automatic intake lets the applications push their changes and the factory process them as they arrive.
  • The Cockpit shows the state of every step and every send; Record lineage says, value by value, where a golden record comes from.

If the summary shows no data product although one exists, your data catalog right may not let you see it: the summary then says so.

The screens

Every screen opens from the project list (the home page) or from a button of another screen. The right in brackets is the least right that opens it (see Who may do what).

Project explorer (VIEW)

The home page: one card per project you may see, with filters, favourites and, for the right users, New project (it opens the wizard) and Delete. It follows the colours of the perspective it is shown in.

Project wizard (VIEW to read, DESIGN to act)

The eight steps described above. A button you may not use is greyed and its tooltip names the right it needs.

Cockpit (VIEW)

The state of every step of a project, of every send, the recent tasks and the rows held back. When the count of held-back rows per entity could not be read in full, the cockpit says "The breakdown below is partial": the total above stays right and only the breakdown is incomplete - open the review screen for the detail.

Held-back rows review (VIEW to read, STEWARD to acknowledge)

The rows a blocking rule or a failed write kept out of the master, with the cause and the rule that stopped each one. Acknowledge a row once it is dealt with; the wizard and the Cockpit count only what is still open.

Proposal review (VIEW to read, STEWARD to decide, DESIGN to apply)

Every proposal of the factory (entities, attributes, mappings, quality rules, matching plans, script constraints) in one list: accept or reject one, a selection or all above a score. A proposal is only applied when you apply it.

Mapping matrix (DESIGN)

Entities in rows, applications in columns: each cell is the mapping of one attribute from one application, with its status, its rule and its checks. The queue at the bottom lists what is still to decide; the arrows go from one item to the next.

Validation desk (DESIGN)

The same decisions as the matrix, sorted by what needs a person first (rules to confirm, anomalies, conditions proposed by the language model), with the evidence for each one.

Feed designer (DESIGN)

One feed at a time, drawn as a diagram: the columns of the application on the left, the fields of the target on the right, the rules and checks between them. Save writes every change of the page at once; a refusal is worded in your language.

Record lineage (VIEW)

For a golden record, where each value comes from: which source rows built it and which merge chose each field. A golden built from many records shows the first contributors with "N of M contributors" and a Next contributors button. When the version of EBX cannot say how a field was chosen, the screen says "merge lineage unavailable on this version". The same view opens from the Actions menu of a record (Record lineage on a record).

Connection settings (administrator)

How the factory reaches the Connectors and data catalog modules: the service account, the secret references and the checks of the link.

Delete a project (administrator)

Lists everything that will go (dataspaces, models, flows, rows) before you confirm; nothing is deleted until you do.

About (VIEW)

The installed version, the build and the links to this guide.

Background tasks

Every long action becomes a task of the project. The banner at the top of the wizard shows the tasks that wait or run, with Stop (a running task finishes its current stage, then stops) or Cancel (a waiting task never starts). Two tasks that write the same part of a project never run at the same time: the second waits its turn.

The Recent tasks list, on the wizard and on the Cockpit, keeps the last tasks of the project with when they ran and how they ended - even after you left the page or the next day. A task that was running when the server restarted reads Interrupted; where it can safely be started again, a Run again button does it.

Besides the loads, these actions are tasks too and no longer hold the page: switching the automatic intake on or off, the check before the build (and its fix), the simulation of a plan, merging every pair above a score, and chaining the loads. The click answers at once with a refusal when there is one (no right, a chain already running); otherwise a task appears in the banner. If the intake switch-on is cut (restart, error, Stop), the intake stays off and the set-up screen says on which applications it was installed: press Switch on again, nothing needs cleaning first.

A task that finished with failures (status Finished with failures) did part of its work: a staging load whose closing writes were refused, a landing whose key could not be set. Its first sentence says what to run again; the same word shows in the notice and in Recent tasks.

When a task you started ends, a notice appears at the bottom right of the screen - in the wizard, and in the proposal review while a task you launched there is still running: the name of the task, whether it finished or failed, the beginning of its result, a link to the Recent tasks list and a Close button. It stays until you close it and is shown once per browser; a task that ended while you were elsewhere is announced the next time you open the wizard, for two hours after it ended.

A button you click is locked until the page answers, and asking again for exactly what is already waiting or running does not start it twice: the second request joins the first.

Run on a schedule

The wizard launches the chain on demand. To run it every night, an administrator plans it in EBX:

  1. In Administration > Workflow management > Workflow launchers, create a launcher on the publication MdmFactoryPipeline, with its input projectCode set to the code of the project.
  2. In Administration > Task scheduler, add a schedule of the built-in task "Launch a workflow" (SchedulerWorkflowLaunchTask) naming that launcher, with the time you want.

Each run then appears in the Cockpit and in the project's Recent tasks like a run launched by hand. The operator guide shipped with the module (OPERATIONS) gives the details.

Deliver to another instance

A project is designed on one instance (development) and delivered to another (test, production) as an EBX Staging archive: models, datasets, flows, scripts, the matching configuration and the distribution. Check the delivery domain, on the summary, lists what the archive will carry and what the target must already have (connections with their own credentials, reference data).

Generating and importing the archive is an administrator's task: the delivery tool shipped with the module builds the archive, and the target imports it with EBX Staging (Administration > Repository management > Staging), dry run first. Data is not part of an archive: once imported, the loads are run on the target.

RightWhat it opens
VIEWThe project list, the Cockpit, the wizard and the proposal review, read only; record lineage.
STEWARDAlso: decide suspect pairs and proposals.
DESIGNAlso: every action that designs or runs a project.
AdministratorThe settings, the access rights, deleting a project, cleaning a step, the delivery check.

A button you may not use is shown greyed, and its tooltip names the right it needs. An administrator gives rights to your roles in the table "Access rights" of the MdmFactory dataset.

When something goes wrong

  • A refusal ("another task of this project is running", "generate the staging first") says what to do next. A message that comes from deeper in the engine is shown under "Details", in English.
  • "Something went wrong (reference MF-...)" means an unexpected error. Nothing is lost: note the reference and give it to your administrator, who finds the full details in the server log under that reference.
  • A task that failed keeps its reason in the Recent tasks list (open "Details").
  • A list that looks empty may be hidden by your data catalog right: the wizard says so when it is the case.

Administrators: the installation, the settings, the background work and the diagnosis are described in the operator guide shipped with the module.
